CPSC 254 Final Project: AI-Powered Web App
This is your capstone for CPSC 254. Design, build, and evaluate an AI-powered web app of your own choosing, ship it to a public GitHub repository, and use the OpenAI API to do it. Kiro (or another AI coding assistant) is encouraged, but the code is yours, and you'll defend it in the written walkthrough and AI disclosure.

The final project is worth 25% of your final course grade. The proposal worksheet and peer review are worth a combined 10 points and will take the place of Quiz 6.

The assignment
Build an AI-powered web app that you'd be proud to put on your portfolio. You choose the domain, what it does, and who it's for.

It must use an LLM in a way that goes beyond Project 4's "text in → structured output once" pattern. Examples of acceptable projects include but are not limited to: retrieval over a corpus you curate, generation with quality controls, multi-turn conversation, function calling, multi-modal input, or another pattern you can defend. You'll measure how well your app's AI behavior works on examples you define, iterate on it, and ship something that runs locally from a README.md with clearly documented setup and run commands.

What to deliver
Submit a public GitHub repository URL via Canvas. The repo must contain:

A web app with a UI: form, loading state, output, error handling. Not a CLI, not a native app. A website.
All source code, plus requirements.txt (or package.json) with pinned dependencies and a .env.example containing only OPENAI_API_KEY.
README.md: what the app does plus setup and run instructions a fresh grader can follow exactly, with example invocations where helpful. Multiple commands are fine if they're unambiguous and in order.
eval/ directory: your eval script and ≥10 labeled test cases (input + expected output or score) that measure your AI behavior with your chosen metric.
REPORT.md: four sections, in order. Total length ~800–1200 words.
What & why (~200–250 words). What the app does, who it's for, and what's hard about getting the AI behavior right.
Iterations (≥3 versions, ~75–150 words each). One labeled subsection per version (V1, V2, V3, …). Each subsection must contain, in this order:
Change: what you changed (prompt, model, retrieval, controls, etc.).
Motivating example: the specific failing case from your eval set that drove the change.
Delta: metric before → after on the same eval set (positive or negative — both are fine if explained).
Conclusion: why the metric moved (or didn't), and what you'd try next.
Code walkthrough (200–300 words). Trace one user action through your code with file:line references. Explain one design decision and one alternative you considered and rejected. Generic "this calls the API" descriptions don't earn full credit.
AI disclosure & safety (~150–250 words). How you used your AI coding assistant (Kiro or otherwise), including 2–3 specific moments it failed and how you recovered. Then 2–3 sentences naming one safety risk specific to your app and the mitigation or accepted limit you chose. Common candidates: prompt injection, hallucination harm, PII exposure, biased output, cost runaway.

Grader environment
Your code will be graded on:

macOS
Python 3.11+ (if Python) or Node 20+ (if Node)
Fresh git clone of your repo
Your README.md's instructions, followed exactly, in order
A grader-supplied .env containing only OPENAI_API_KEY
Required keys policy. The grader supplies OPENAI_API_KEY and nothing else. If your app needs any other API key to start (Pinecone, Weaviate Cloud, LangSmith, Supabase, Twilio, etc.), the grader can't run it. Pick a stack that stays inside this constraint:

For RAG / vector search, use a local vector store (e.g., Chroma in embedded mode or FAISS) — anything that lives on disk in your repo.
For other services, prefer libraries that run locally, like SQLite over hosted Postgres or local files over S3.
The OpenAI API is the one exception.
The grader will not debug your setup. If your app does not start or the main feature does not work after following your README, you receive 0 in "App works end-to-end" and 0 in "UI/UX", a 20-point penalty.

Test your README on a clean directory before submitting. Clone your repo into a fresh folder, follow your own instructions exactly, and confirm the app runs with a brand-new .env.
